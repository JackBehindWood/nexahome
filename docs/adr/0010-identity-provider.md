# 0010. Identity provider: Pocket ID

* **Status:** Proposed
* **Date:** 2026-10-22 (amended 2026-10-22 after P2.5 session 2 and 2026-10-23 after session 3; still Proposed)

## Context
P2.5 wants one login for NexaHome apps, two roles (`admin`, `users`) and a reserved `agents` group that is never admin and has no client access. Requirements R1 to R10 are in the P2.5 plan. Apps stay replaceable clients: they rely only on an OIDC discovery URL, a client id and secret, and a `groups` claim (R9). Spike on 2026-10-21 and 2026-10-22 (macOS, Colima 2 CPU / 2 GB, Safari; the throwaway project and its volumes are removed). Related: [ADR 0007](0007-stack-contract.md), [ADR 0008](0008-backup-tool.md), [ADR 0011](0011-edge-and-local-hostnames.md).

## Decision (Proposed)
Use Pocket ID as `stacks/identity`: passkey-only logins, OIDC, groups restrict access per client, SQLite. Pin `ghcr.io/pocket-id/pocket-id:v2.18.0-distroless`. Not v2.19.0: it was released hours before the spike. Authelia stays the fallback (not measured).

Interface a client must provide: discovery URL `http://id.${NEXAHOME_DOMAIN}:${EDGE_PORT}/.well-known/openid-configuration`, client id, client secret, callback `<app>/openid/callback`. The issuer carries the edge port, so it changes with the hostname or port ([ADR 0011](0011-edge-and-local-hostnames.md)).

| Item | Measured |
| :-- | :-- |
| Image | arm64 manifest present; 110 MB; BSD-2-Clause; user 65532 built in; own `healthcheck` subcommand (90 s interval) |
| Hardening | runs with `read_only`, `cap_drop: ALL`, `no-new-privileges`, no published port |
| Idle RAM | 17 MiB (two readings, the second after a restart) |
| Data path | The image has no `/app/data`, so a new volume there is root-owned and a non-root start fails ("unable to open database file"). Works: mount the volume at the image's built-in non-root home directory (exists, owned by 65532, copied into a new volume) and point `DB_CONNECTION_STRING`, `UPLOAD_PATH`, `GEOLITE_DB_PATH` into it. Restore through `make restore` not tested |
| Outbound | `ANALYTICS_DISABLED` and `VERSION_CHECK_DISABLED` set: no outside connection seen (established sockets, log scan). Internal UDP 1414 (task runtime), not published |
| Recovery | `docker exec <container> /app/pocket-id one-time-access-token <user>` works without a shell; prints a one-hour sign-in link (used) |
| Seeding | `STATIC_API_KEY` (admin-level) created groups, users, client `actual` with a chosen id, and a client secret (`POST /api/oidc/clients/<id>/secrets`, several allowed, so rotation works). The secret is generated by the provider and returned once, so a client's `.env` cannot be a pure Git file |
| Group rule | A client needs `isGroupRestricted: true`. With only the allowed-groups list set, a user in no group was authorised (audit log). After the flag: `access_denied`, "You are not allowed to access this service" (agentx in `agents`; mallory) |
| Passkey | Registered and signed in on `http://id.*.localhost:<port>` in Safari (reported by the owner). Chrome and Firefox not installed here, not tested |
| Actual | Login through the `http://` issuer works for the first user, who becomes server owner (callback logged). An unknown user is refused with 400 `openid-grant-failed`. Matching claim and the full path for a second allowed user: not tested |

## Failure modes
- Pocket ID exited once (code 1, "host is not registered" from its internal health check) about 35 minutes after start. Cause not established. Needs `restart: unless-stopped`; data was intact after the restart. While it was down, Actual's page was blank in the browser (likely, not proven).
- Provider down: new SSO logins fail, apps with a valid session and the Actual password fallback keep working (R5, to be verified in S3).
- Lost `ENCRYPTION_KEY`: a restored database is unusable; keep it with the restic password.

## Consequences
- **Amendment, session 2 (owner decided):** the one sign-in page is Pocket ID's own My Apps page (since v1.7.0, per its documentation); the portal stays an open, read-only status board on loopback and is not gated. Gating it (forward auth through the edge, OAuth2 Proxy or similar) moves to the leaving-loopback gate in ADR 0011. Measured in session 2 (owner's report, not independently observed): `user` sees only Actual Budget, `admin` also saw a temporary admin-only test client (deleted). The launch links gave the edge's 404 because no route for them exists yet.
- **Access tiers (Proposed):** status board open on loopback; apps with personal data behind SSO with a long session (set to 1440 minutes; Pocket ID has one session setting for everyone, so there is no shorter admin session); machines and agents never sign in interactively.
- **Agents (Open):** agents get no account yet; the `agents` group is empty and has no client access. Planned path: a machine client with the client-credentials grant and scoped permissions (Pocket ID "custom API permissions"), which the documentation describes for a newer release than the pinned one; not verified. An API key is the wrong tool (admin power).
- **API key contract (Proposed):** a key has an id, an account type (admin, user, agent), scopes, an expiry and a revoked flag; the secret is shown once. While everything is free every account has every scope; a later paid tier would map a group to extra scopes. No issuer is built until a first resource server exists. A paid tier touches the Confirmed rules on open source and no subscriptions: Deferred by the owner on 2026-10-22; nothing changed and everything stays free.
- **Registration:** by hand in the UI with a field table in the identity README; `STATIC_API_KEY` is not set. A session-2 key created in the UI (named, with an expiry date, revocable) was used once to configure the instance and was revoked afterwards; its scope is admin-level in practice (not documented). Scripting is reconsidered at the third client.
- **Owner feedback (2026-10-22):** the test flow (one-time links, private windows, passkey prompts, "Something went wrong" in Actual when refused) felt poor, and the owner wants one command-centre page to sign in to, usable by an admin and an agent. The daily path (one passkey sign-in, then tiles) was measured only for one user. Agents never use passkeys (R2), so an agent login to the page needs a separate mechanism. **Open:** gate the portal itself, or only the apps; owner to decide.
- Settled in S2: client by hand in the UI; no static API key.
- Pinned `v2.18.0`; `v2.19.1` (2026-10-22) only bumps the base images. Pocket ID has many 2026 security advisories fixed up to v2.15.0; none newer was listed on 2026-10-22. Dependabot proposes later tags.
- A one-time access token satisfied the passkey step-up check before 2.6.0; treat the host-side recovery command as admin power.
- In S2 the container ran 40 minutes with no restart (restarts 0; the S1 exit was not seen again, not proven gone). `restart: unless-stopped` is set.
- Superseded by session 3: `ACTUAL_USER_CREATION_MODE=login` is set in the stack, so the Actual user is created at first sign-in (Basic role); `manual` stays available.
- R6: identity adds 17 MiB (see ADR 0011 for the total).
- **Amendment, session 3 (measured 2026-10-23, Actual 26.10.0, Safari, owner's browser reports plus the provider audit log and the Actual log):**
  - R1, R3 met: `admin` (becomes Actual owner) and `user` (Basic) both signed in through My Apps. A member removed from `users` loses the tile in My Apps and is refused with "You are not allowed to access this service"; no code is issued and Actual gets no callback. Refusals are not in the audit log (successes only), so the evidence is the missing `CLIENT_AUTHORIZATION` plus the Actual log.
  - R2 met: `agentx` (group `agents`, no passkey) sees no apps and cannot finish an app sign-in; the interaction needs a passkey login, and a one-time link does not count.
  - **Every account needs a passkey.** A user signed in only through a one-time link gets a blank interaction page when launching an app (hypothesis confirmed when the passkey was added). The identity README now says so. Agents therefore cannot sign in to apps interactively, as intended.
  - **Actual stores its login method and a copy of the client secret in its own database;** the OpenID variables only prefill a one-time switch. Emptying them is not a rollback (measured). Rollback and recovery are host-side Actual scripts ([runbook](../runbooks/identity-recovery.md)). R5 is met as: password login still works and the budget data was intact after a password reset; removing the variables is not the switch.
  - **Actual sessions never expire by default and survive provider group changes.** Proposed: `ACTUAL_TOKEN_EXPIRATION=86400` (set in the stack, applies to new logins). Access removal is only effective for new sign-ins until the session ends.
  - Boot order: Actual started with edge and identity down logs `configuration-error`, stays healthy (0 restarts) and accepts OpenID logins after they return, with no restart. Provider down: existing sessions work, new logins fail (`openid-setup-failed`).
  - Recovery drill of 2026-10-23: one-time link, passkey removed then added (same Keychain refuses add-first), sign-in with the new passkey, Actual opened.
  - Not verified: a second authenticator, Chrome, Firefox, Linux; whether the first-login owner rule can be avoided on a fresh Actual instance; a rotated client secret end to end; the S1 provider exit cause.

## Alternatives
Authelia (file users and forward auth; fallback), Authentik, Keycloak, Zitadel (need Postgres; not measured), Kanidm (larger operating model), no provider in P2.5 (portal only; each app keeps its own login: the cheaper way back, cost is a login per app and no roles), a custom login (rejected: no custom login code).
